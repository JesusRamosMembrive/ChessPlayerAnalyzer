    Flujo de Análisis Celery - ChessPlayerAnalyzer

    Audiencia: Desarrolladores, DevOps Última actualización: 2025-09-13 Estado: Completo

    Documentación completa del sistema de procesamiento asíncrono con Celery para análisis de ajedrez, incluyendo arquitectura de tareas, flujos de trabajo y manejo de errores.

    <¯ Objetivo

    El sistema Celery proporciona: - Procesamiento asíncrono de análisis de partidas y jugadores - Escalabilidad horizontal con múltiples workers - Tolerancia a fallos con retry automático y manejo de errores - Monitoreo en tiempo real de progreso y estado - Cancelación segura de tareas en ejecución

    <× Arquitectura de Celery

    Configuración Principal

    # Broker y Backend: Redis
REDIS_URL = "redis://redis:6379/0"
celery_app = Celery("chess_tasks", broker=REDIS_URL, backend=REDIS_URL)

# Colas especializadas
celery_app.conf.task_queues = (
    Queue("default", max_priority=10),   # Análisis estándar
    Queue("torch", max_priority=10),     # Machine Learning
)

# Timeouts y retries
TASK_SOFT_TIME_LIMIT = 1800  # 30 minutos
TASK_TIME_LIMIT = 1860       # 31 minutos (hard limit)
TASK_MAX_RETRIES = 3

    Workers Especializados

    • default queue: Análisis Stockfish, procesamiento de partidas
    • torch queue: Modelos PyTorch, clasificación ML
    • Prioridades: 0 (alta) a 9 (baja)

    =Ë Tareas Principales

    1. process_player_enhanced

    Tarea orquestadora principal para análisis completo de jugadores.

    Configuración: 

    @celery_app.task(
    name="process_player_enhanced",
    bind=True,
    autoretry_for=(Exception, SoftTimeLimitExceeded),
    retry_backoff=True,
    retry_kwargs={"max_retries": 3},
    soft_time_limit=1800,
    time_limit=1860,
)

    Flujo interno: 1. Descarga de partidas - fetch_games(username, months) 2. Creación de registros - Game objects en base de datos 3. Construcción de chains - Una por partida 4. Ejecución paralela - group() de todas las chains 5. Agregación final - chord() con callback analyze_player_detailed

    Manejo de cancelación: 

    def _is_aborted(task, player_username=None):
    # 1. Check Redis cancellation flag (fastest)
    if player_username:
        cancellation_key = f"cancel:{player_username}"
        if redis_client.get(cancellation_key):
            return True

    # 2. Check Celery internal flags
    if hasattr(task, "is_aborted"):
        return task.is_aborted()

    return False

    2. analyze_game_task

    Análisis individual de partida con Stockfish.

    Parámetros: - pgn_text - Texto PGN de la partida - game_id - ID opcional (se crea si es None) - move_times - Tiempos por movimiento (Chess.com) - depth - Profundidad Stockfish (default: 12) - multipv - Líneas múltiples (default: 3)

    Proceso: 1. Validación PGN y creación/búsqueda de Game 2. Inicialización Stockfish con parámetros configurados 3. Análisis por movimiento: - Evaluación antes del movimiento - Evaluación después del movimiento - Ranking de la jugada (1=mejor, 2=segunda, etc.) - Centipawns perdidos - Tiempo gastado 4. Almacenamiento en tabla MoveAnalysis 5. Progress updates cada 5% de movimientos

    Ejemplo de análisis: 

    # Para cada movimiento
info_before = engine_sf.analyse(board, chess.engine.Limit(depth=12), multipv=3)
eval_before = info_before[0]["score"].white().score() or 0
best_move = info_before[0]["pv"][0]

# Ejecutar jugada y evaluar
board.push(move)
info_after = engine_sf.analyse(board, chess.engine.Limit(depth=12))
eval_after = info_after["score"].white().score() or 0

# Calcular ranking y pérdida
rank = next((i for i, pv in enumerate(info_before) if pv["pv"][0] == move), 3)
cp_loss = abs(eval_before - eval_after)

    3. analyze_game_detailed

    Cálculo de métricas avanzadas por partida.

    Input: game_id del análisis Stockfish completado Output: Registro GameAnalysisDetailed con métricas

    Métricas calculadas: - Quality: ACPL, match rate, IPR, precision bursts - Timing: Varianza, correlaciones, spikes, uniformidad - Opening: Entropía, novelty depth, breadth - Endgame: Tablebase accuracy, conversión - Anomaly: Scores de detección, flags de sospecha

    Módulos utilizados: 

    from app.analysis import (
    aggregate_quality_features as q_feats,
    aggregate_time_features as t_feats,
    aggregate_opening_features as o_feats,
    aggregate_endgame_features as e_feats,
)

    4. analyze_player_detailed

    Agregación final y análisis longitudinal del jugador.

    Trigger: Chord callback después de completar todas las partidas Input: username del jugador analizado Output: Registro PlayerAnalysisDetailed

    Análisis realizados: - Agregaciones básicas - Promedios, desviaciones, rangos - Análisis longitudinal - Tendencias, change points, ROI - Comparación con peers - Deltas vs. rangos ELO similares - Risk assessment - Score final y factores de riesgo - Clustering ML - Asignación a grupos de comportamiento

    =' Herramientas de Monitoreo

    Progress Tracking

    def task_progress(task, current, total, username=None):
    """Update task progress and notify via WebSocket"""
    percentage = int((current / total) * 100)

    # Update Celery task state
    task.update_state(
        state='PROGRESS',
        meta={'current': current, 'total': total, 'percentage': percentage}
    )

    # Notify via Redis/WebSocket
    if username:
        notify_ws(username, {
            'progress': percentage,
            'current': current,
            'total': total
        })

    Cache System

    def cache_get(task_name, args, kwargs):
    """Retrieve cached result for task"""
    cache_key = f"task_cache:{task_name}:{hash((tuple(args), tuple(sorted(kwargs.items()))))}"
    return redis_client.get(cache_key)

def cache_set(task_name, args, kwargs, result):
    """Store task result in cache"""
    cache_key = f"task_cache:{task_name}:{hash((tuple(args), tuple(sorted(kwargs.items()))))}"
    redis_client.setex(cache_key, 3600, json.dumps(result))  # 1 hour TTL

    WebSocket Notifications

    def notify_ws(username, data):
    """Send real-time notification via Redis pub/sub"""
    channel = f"player:{username}"
    message = {
        'timestamp': datetime.now(timezone.utc).isoformat(),
        'username': username,
        **data
    }
    redis_client.publish(channel, json.dumps(message))

     Manejo de Errores

    Retry Strategy

    autoretry_for=(Exception, SoftTimeLimitExceeded)
retry_backoff=True          # Exponential backoff
retry_backoff_max=600       # Max 10 minutes
retry_jitter=True           # Add randomness
retry_kwargs={"max_retries": 3}

    Timeout Handling

    • Soft limit (30min): SoftTimeLimitExceeded  retry automático
    • Hard limit (31min): Terminación forzosa, posible pérdida de datos
    • Graceful shutdown: Verificación periódica de _is_aborted()

    Error States

    # En Player.status
"pending"  # Análisis en progreso
"ready"    # Completado exitosamente
"error"    # Error no recuperable
"stopped"  # Cancelado por usuario

# En task results
{"status": "revoked"}     # Cancelación detectada
{"status": "cancelled"}   # Game eliminado durante análisis
{"status": "insufficient_data"}  # Muy pocas partidas

    =Ê Métricas de Rendimiento

    Tiempos Típicos

    • Partida individual: 2-5 minutos (40 movimientos × depth=12)
    • Jugador (150 partidas): 4-8 horas (depende de workers disponibles)
    • Análisis detallado: 30-60 segundos por partida
    • Agregación final: 2-5 minutos por jugador

    Optimizaciones

    • Cache Redis: Evita reanalizar partidas idénticas
    • Parallel processing: Group/chord para máximo paralelismo
    • Priority queues: Tareas críticas van primero
    • Batch inserts: Múltiples MoveAnalysis en una transacción

    = Consideraciones de Seguridad

    Isolation

    • Process isolation: Cada worker en contenedor separado
    • Resource limits: Memory/CPU limits via Docker
    • Task timeouts: Previenen workers zombie

    Data Safety

    • Transactional: Commits atómicos por partida
    • Graceful cancellation: Estado consistente al cancelar
    • Error recovery: Retry automático con backoff
